## 3. 詳細

### 3.1 Vitest 起動コストの支配

`vp test run` の cold/warm 差は 6.897 → 6.876 s とほぼ無く、Vitest は OS ファイルキャッシュよりプロセス自身の起動コスト（jsdom 環境構築 + transform + import）が支配的。`Duration` 内訳の中央値は概ね `transform 14ms / import ~100ms / tests ~7.7s / environment 0ms`（node 環境）。

(d-3) の preview.tsx シナリオ（jsdom 環境含む 2 テスト）が `import 957ms / environment 748ms / tests 307ms` で計約 1.5 s に収まっているのに対し、(d-2) のように依存元が広い `src/server/files.ts` を staging すると 5 テストで約 6.94 s と全件 (28 テスト 6.88 s) と差がない。要するに **「テスト数が減ってもコスト下がらないレンジ」が中核モジュールには存在する**。

### 3.2 `--changed` の挙動検証（plan.md L93）

| 確認内容                                                           | 結果                                                                             |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| `tests/files.test.ts` を staging し `vp test run --changed` を実行 | 関連 5 ファイル抽出。所要 6.94 s（全件と同等）                                   |
| `src/server/files.ts` を staging し同コマンド                      | 関連 5 ファイル抽出（`tests/files.test.ts` 含む）。依存関係追跡が機能            |
| `README.md` を staging し同コマンド                                | 関連 0 ファイル → "No test files found" で exit 0。pre-commit 上は問題なくスルー |
| `src/client/components/preview.tsx` を staging し同コマンド        | 関連 2 ファイル抽出。所要 1.50 s                                                 |

→ vitest の `--changed` / `related` は staged ファイルから依存先テストを正しく抽出する。落とし穴（誤判定 / 実行失敗）は確認されず、選択ロジック自体は動作する。問題はあくまで「中核モジュールでは全件と所要が変わらない」という Vitest 起動コスト構造側。

### 3.3 計測ノイズと信頼性

- warm 3 回の標準偏差は (a) ±0.10 s、(b) ±0.07 s、(c) ±0.04 s、(e) ±0.17 s と小さく、median 採用で代表値の安定性は十分。
- (d-3) のみ最大値 1.733 s が他 2 回（1.463 s / 1.503 s）と離れているが、jsdom 起動の cold 影響と推定。min 1.463 s / median 1.503 s で、median を代表値として採用。
- pnpm の `WARN  Issue while reading "/Users/mba/.npmrc"` が毎回出力されるが Vitest 起動時間に影響する性質ではないため計測値からは除外して評価した。

## 5. 結論

**不採用**。`lefthook.yml` は変更しない。

### 5.1 不採用の理由（要約）

1. (e) 全テスト追加で +7.24 s（中央値）。事前固定の +5 s 閾値を超過
2. (d) `--changed` 案でも、中核モジュール（依存被参照が広いファイル）staging 時に +6.94 s。最良 / 最悪のばらつき大で、+5 s 閾値超過
3. CI（`.github/workflows/ci.yml`）で push/PR 時にテスト実行が確保されており、pre-commit にゲートを置かなくとも検証経路が存在
4. pre-commit 合計 ~10 s は、現行 ~2.8 s からの体感劣化が大きく、`git commit` の頻度を下げる副作用リスクがある

### 5.2 採用しなかったが残しておく観点（次タスクで再考可能）

- **pre-push hook の新設**: `git push` 時なら +7 s の許容度が高く、ローカル CI の代替として機能する余地がある。本 issue スコープ外だが、#92 系列で扱う価値あり
- **Vitest 起動コストの根本短縮**: vite-plus / vitest 側で jsdom 環境の事前ウォーム / プロセス常駐モードが入れば再評価可能（現状は外部ライブラリ依存）
- **閾値の見直し**: +5 s / 合計 15 s は本 issue で事前固定した値。チームが pre-commit に許容する待ち時間が変われば、(e) 案 (+7.24 s, 合計 10.09 s) は再採択候補になる

## 6. 影響と次タスク

- **本 issue の成果物**: 本レポートのみ。`lefthook.yml` 変更なし、`src/**` 変更なし、自動テスト追加なし
- **#92-D（ルール反映）への申し送り**: 「pre-commit テストは現状不採用。CI 側で test / test:e2e を維持。pre-push 案は #92 系列の追加タスクとして必要なら検討」という方針を `specv-conventions` 等のポリシーに反映するかは #92-D 側で判断
- **再計測トリガー**: vite-plus / vitest が常駐モード（または `--isolate=false` の安定化）を実装した場合、(c) のコストが大幅に下がる可能性があるため、本レポートを参照して再計測
