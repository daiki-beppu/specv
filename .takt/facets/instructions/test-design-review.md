## レビュー観点

### 1. ケース一覧の網羅性

- Happy / Edge / Error の 3 区分すべて埋まっているか
- 想定される境界値・並行・例外パスが過不足なく拾われているか
  - 入力: 空 / 極小 / 極大 / 不正型 / 並行
  - 状態: 未初期化 / 初期化済 / 終了済
  - 出力: 正常 / エラー / 部分成功
- 1 行 1 ケースの粒度を維持できているか (複合ケースは分割されているか)
- describe / it タイトルが日本語で AAA に分解可能な粒度か

### 2. 責務分担マトリクスの妥当性

- Unit / E2E の判断根拠が明確か
- 純粋ロジックを E2E に振っていないか (過剰結合 / コスト超過)
- DOM 描画・実ブラウザ依存を Unit に振っていないか (検証不能)
- 重複検証 (Unit と E2E の両方で同じ振る舞い検証) になっていないか

### 3. specv 規約整合

- `tests/test-utils.ts` の既存ヘルパーで書ける前提が明示されているか
- 命名 (日本語 describe / it, ファイル名 `*.test.ts(x)`) が specv 流に揃うか
- specv-conventions の TDD サイクル (Red→Green→Refactor) を Red 段階で書ける粒度か

### 4. 不確定要素の取り扱い

- 「要ユーザー確認」事項が末尾に列挙されているか
- 設計表に推測値が混入していないか

## アウトプット (test-design-review.md)

- 冒頭で `approved` または `needs_fix` を明記
- `needs_fix` の場合: 指摘ごとに以下を列挙
  - 対象ケース ID または セクション番号
  - 問題 (観点 1〜4 のどれに該当するか明記)
  - 修正提案 (具体的に)
